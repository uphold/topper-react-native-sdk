# @uphold/topper-react-native-sdk

Seamless integration of [Topper](https://topperpay.com) into React Native applications.

This SDK renders the Topper flow inside a [`react-native-webview`](https://github.com/react-native-webview/react-native-webview) and bridges events and handlers between Topper and your app in a React Native `<TopperWebView>` component.

## Installation

```sh
npm install @uphold/topper-react-native-sdk
```

### Peer dependencies

This package relies on the following peer dependencies, which your app must install:

```sh
npm install react react-native react-native-webview
```

Minimum versions: `react >=18`, `react-native >=0.70`, `react-native-webview >=13`.

`react-native-webview` contains native code. For bare React Native, run `npx pod-install` after installing; for Expo, install it with `npx expo install react-native-webview`.

## Quick start

Import the `<TopperWebView>` component with inline props:

```tsx
import { TopperWebView, TOPPER_ENVIRONMENTS } from '@uphold/topper-react-native-sdk';

export default function TopperScreen() {
  return (
    <TopperWebView
      bootstrapToken="YOUR_BOOTSTRAP_TOKEN"
      config={{ environment: TOPPER_ENVIRONMENTS.SANDBOX }}
    />
  );
}
```

> The component needs a sized container. Use explicit styling otherwise the WebView renders with zero height and nothing appears.

The `bootstrapToken` is a signed JWT generated by your backend. See the [Topper widget documentation](https://docs.topperpay.com/widgets) for how to create one.

## Usage

Pass configuration and event handlers directly as props. The component creates and manages everything internally and cleans up on unmount.

> Configuration is read once. The `config` and the set of registered `handlers` / event props are captured when the component first mounts and the WebView loads — changing them afterward does not rebuild the flow. (Event/handler callback *implementations* may change freely; only the registered set is fixed.)

```tsx
import { TopperWebView, TOPPER_ENVIRONMENTS, TOPPER_THEMES, TOPPER_FLOWS } from '@uphold/topper-react-native-sdk';

<TopperWebView
  bootstrapToken="YOUR_BOOTSTRAP_TOKEN"
  config={{
    environment: TOPPER_ENVIRONMENTS.SANDBOX,
    theme: TOPPER_THEMES.LIGHT,
    active_flow: TOPPER_FLOWS.CRYPTO_ONRAMP,
  }}
  onEvent={({ name, data }) => console.log('any event', name, data)}
  onOrderPlaced={({ data }) => console.log('placed', data)}
/>
```

### Props

| Prop | Type | Description |
| --- | --- | --- |
| `bootstrapToken` | `string` | A single bootstrap token (JWT) generated by your backend. |
| `bootstrapTokens` | `string[]` | Multiple bootstrap tokens (joined with `;`). Use instead of `bootstrapToken`. |
| `config` | `Config` | Configuration object (see [Config](#config)). |
| `handlers` | `{ [name: string]: Handler }` | Request/response handlers Topper can call (see [Handlers](#handlers)). |
| `inAppBrowser` | `InAppBrowser` | Adapter for opening Topper's external steps (Google Pay, social sign-in) in an in-app browser (see [External tabs / popups](#external-tabs--popups)). |
| `onEvent` | `EventHandler` | Catch-all handler — receives every event with `{ name, data }`. |
| `onOrderContinueButtonClicked` | `EventHandler` | Fired when the user taps continue on the order screen. |
| `onOrderPlaced` | `EventHandler` | Fired when an order is placed. |
| `onOrderWalletSendButtonClicked` | `EventHandler` | Fired on the off-ramp wallet send step. |
| `onWidgetContinueButtonClicked` | `EventHandler` | Fired when the user taps continue on the widget. |
| `style` | `StyleProp<ViewStyle>` | Style applied to the underlying WebView. |
| `webViewProps` | `Partial<WebViewProps>` | Escape hatch for any [`react-native-webview` prop](https://github.com/react-native-webview/react-native-webview/blob/master/docs/Reference.md). |

## API

### Config

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `environment` | `TOPPER_ENVIRONMENTS` | `production` | `production` or `sandbox`. Selects the Topper base URL. |
| `theme` | `TOPPER_THEMES` | — | `light` or `dark`. |
| `locale` | `TOPPER_LOCALES` | — | `en`, `en-US`, `pt`, `pt-BR`, `es`, `es-ES`. |
| `initial_screen` | `TOPPER_INITIAL_SCREENS` | `null` | `authentication`. |
| `active_flow` | `TOPPER_FLOWS` | `null` | `crypto_onramp` or `crypto_offramp`. |
| `baseUrl` | `string` | — | Overrides the base URL (e.g. a local Topper instance for development). When set, takes precedence over `environment`. |

The platform (`is_ios_webview` / `is_android_webview`) is detected automatically from `Platform.OS` — you do not need to set it.

### Events

Accessible via `TOPPER_EVENTS`:

| Event | Value |
| --- | --- |
| `ALL` | `*` |
| `ORDER_CONTINUE_BUTTON_CLICKED` | `orderContinueButtonClicked` |
| `ORDER_PLACED` | `orderPlaced` |
| `ORDER_WALLET_SEND_BUTTON_CLICKED` | `orderWalletSendButtonClicked` |
| `WIDGET_CONTINUE_BUTTON_CLICKED` | `widgetContinueButtonClicked` |

Handlers registered on `ALL` receive `{ name, data }`; handlers for a specific event receive `{ data }`.

> **Note:** only the events you register are requested from Topper (they are serialized into the URL). Some events are only emitted by Topper when their specific name is registered — registering only `ALL` (`onEvent`) is not sufficient to receive those. Register the specific handler (e.g. `onOrderContinueButtonClicked`) to guarantee delivery.

> **The button-click events are interception points, not just notifications.** `onOrderPlaced` is informational, but registering `onOrderContinueButtonClicked` (and the other `*ButtonClicked` events) tells Topper to **hand control to your app instead of performing its own default navigation**. Your handler is then responsible for what happens next (e.g. navigating, calling your backend). If you register one but don't act on it, the user can be left on a stalled button. Only register these if you intend to take over that step.

### Handlers

Handlers are the **request/response** counterpart to events: Topper calls a function in your app and awaits its result. Use them when Topper needs data only the host app can provide (e.g. a fresh token or a user decision).

The returned value is sent back to Topper; if the handler throws, the error is propagated and rejects Topper's promise. As with events, only the handler names you register are requested from Topper (they are serialized into the URL).

```tsx
<TopperWebView
  bootstrapToken="YOUR_BOOTSTRAP_TOKEN"
  config={{ environment: TOPPER_ENVIRONMENTS.SANDBOX }}
  handlers={{
    getFreshToken: async () => {
      const token = await fetchTokenFromBackend();

      return { token };
    },
  }}
/>
```

### External tabs / popups

Topper pushes some steps — Google Pay, social sign-in, certain payment redirects — into a **separate tab** via `window.open` / `target=_blank`. The component sets `setSupportMultipleWindows` and handles `onOpenWindow`. **No setup is required** — by default it opens the requested URL in the device's **system browser** (`Linking.openURL`), so these steps work out of the box.

The `inAppBrowser` prop is **optional** and only improves UX: an in-app browser stays inside your app, shares the session, and auto-dismisses on redirect (the system browser leaves your app and the return is clunkier).

#### Using an adapter

```tsx
import * as WebBrowser from 'expo-web-browser';

<TopperWebView
  bootstrapToken="YOUR_BOOTSTRAP_TOKEN"
  inAppBrowser={{ open: url => WebBrowser.openBrowserAsync(url) }}
/>
```

If you need full control, override `onOpenWindow` (or `setSupportMultipleWindows`) via `webViewProps` — it takes precedence over the built-in handling.

### Apple Pay (iOS)

To let the WebView present the Apple Pay sheet, enable it on the underlying WebView via `webViewProps`:

```tsx
<TopperWebView
  bootstrapToken="YOUR_BOOTSTRAP_TOKEN"
  config={{ environment: TOPPER_ENVIRONMENTS.SANDBOX }}
  webViewProps={{
    enableApplePay: true
  }}
/>
```

**Requirements**

- **iOS 16 or later** — `enableApplePay` does not work reliably on earlier versions.
- **Apple Pay merchant configuration in your native app** — add the Apple Pay capability, a Merchant ID, and the merchant entitlement to your iOS app. The SDK cannot provide these.
- The merchant domain-association file is hosted by Topper, so there is nothing to configure for that.

> **Important — Apple Pay disables the events/handlers bridge.** `react-native-webview`'s `enableApplePay` turns off all JavaScript injection (`injectedJavaScript`, `injectJavaScript`, and the `window.ReactNativeWebView` messaging bridge). As a result, **`onEvent`, the `on*` event props, and `handlers` are not delivered** while Apple Pay is enabled. This is a documented `react-native-webview` limitation, not specific to this SDK. When you enable Apple Pay, rely on your backend (webhooks) or a redirect to detect that an order completed — not on JS events.

If you need **both** Apple Pay **and** completion events, the supported alternative is to present Topper in a full browser context — the system browser, or an `SFSafariViewController` with the `is_safari_view_controller=1` query parameter — instead of the inline `<TopperWebView>`. Apple Pay works there because it is a full Safari environment, but that context likewise has no events/handlers bridge, so handle the return via a redirect or universal link. See the [Topper mobile integration guide](https://docs.topperpay.com/mobile).

## How it works

Topper runs as a web app inside the WebView and communicates with your app over the WebView's message channel. Topper's web messaging targets a host window (`window.parent` / `window.opener`), which doesn't exist for a top-level WebView document — so the SDK injects a small bridge script (before the page loads) that connects that messaging to React Native's `window.ReactNativeWebView` channel. Messages are routed by a `source` field.

**Events** (`source: "@topper-web-sdk-event"`) are one-way, Topper → app. Topper emits a message like:

```json
{ "name": "orderPlaced", "payload": { "...": "..." }, "source": "@topper-web-sdk-event" }
```

The SDK validates the source and dispatches to your registered event props (`onOrderPlaced`, etc.) and the catch-all `onEvent`.

**Handlers** (`source: "@topper-web-sdk-handler"`) are request/response. Topper posts a `resolveHandler` request — `{ "name": "resolveHandler", "payload": { "handlerName": "...", "data": ... }, "source": "@topper-web-sdk-handler" }`. The SDK runs your registered handler and posts the result back into the WebView, which settles Topper's promise. If your handler throws, the error is serialized to `{ error: { name, message } }` and rejects that promise.

The `is_ios_webview` / `is_android_webview` query params are set automatically from `Platform.OS`. They tell Topper it is running inside a native WebView (which affects things like payment-method presentation) — they do **not** control the message transport.

## Requirements & notes

- **Container size** — the WebView needs a sized parent.
- **Cloudflare Turnstile** — Topper uses Cloudflare Turnstile for bot prevention, which renders inside `about:blank` / `about:srcdoc` frames. The component **allows these origins by default** (`['https://*', 'http://*', 'about:blank', 'about:srcdoc']`), so no setup is required. If you need a different policy, override it via `webViewProps`:
  ```tsx
  webViewProps={{
    originWhitelist: ['https://*', 'http://*', 'about:blank', 'about:srcdoc'],
  }}
  ```
- **External tabs / popups** — see [External tabs / popups](#external-tabs--popups).
- **Apple Pay (iOS)** — opt-in via `webViewProps`, with tradeoffs; see [Apple Pay (iOS)](#apple-pay-ios).
- **Camera & microphone permissions** — required for identity verification (Veriff). Configure these in your app's native permissions.
- **`injectedJavaScriptBeforeContentLoaded` is merged, not replaced** — the SDK injects its own bridge script there; if you pass your own via `webViewProps`, the SDK's runs first and yours is appended. `onMessage` is owned by the SDK and cannot be overridden.
